# Commit messages, and what a pull request says about itself

The reading has never read the version history's prose. A commit message is a statement of what a change was for, written by the person who made it, at volume — tens of thousands of statements in a mature repository — and none of it reaches any scope today. Two uses, ordered cheapest first, and a third that is a weighting question rather than a source.

Both uses carry the hazard [supplied text](SUPPLIED_TEXT.md) states before anything is built: **an author who describes the domain in a description gets that description handed back as a finding.** A commit saying `add FIX order routing` would place a repository in finance by assertion. So commit prose is never pooled into the tree's reading: it is its own scope, with its own chance thresholds, reported with the code's reading beside it and without it — the shape the pull request path already ships. The prose arrives the way a pull request arrives: a fetch step writes it to a pinned file, because the library reads no `.git` and no network. For the evaluation members the fetch is free — the clones are local, and `git log` needs no token.

## 1. What a pull request says beside what it writes

The pull request path publishes what a pull request's changed files *write* — its `pullRequests` entry in [the export](THE_EXPORT.md), signals against the pull request's own permutation null. This half reads what the same pull request *says*: its title, its description, and the messages of its commits, fetched by `fetch-pull-requests.sh` beside the files it already pins and read as prose through the pipeline any documentation takes.

That yields two distributions over the same subject space for one pull request — stated and written — and **the comparison is the finding**: the Jensen–Shannon divergence between them, bounded at 1 bit like every divergence this library reports. A reviewer acts on *the description says configuration loading and the code writes configuration loading* exactly as they act on its negation. The stated words never enter the written reading and the written words never enter the stated one, so neither answers for the other.

The research frames the question the same way. Message-against-change inconsistency is a current benchmark task ([CodeFuse-CommitEval](https://arxiv.org/pdf/2511.19875)), it is load-bearing for reviews of machine-authored pull requests ([message-code inconsistency in agent-authored pull requests](https://arxiv.org/pdf/2601.04886)), and the taxonomy of what a message should state — what changed, and why — is measured in [What Makes a Good Commit Message?](https://arxiv.org/pdf/2202.02974). One caution from the tangled-changes literature: a pull request mixing two concerns states one of them, so a divergence is evidence of a gap, never by itself evidence of a bad description.

**The bar must be derived.** A pull request's prose may be forty words, and a fixed divergence threshold would be a chosen bound. The null is the same family the path already runs: what divergence chance produces between the written signals and a stated sample of this size, at the reading's seed.

**What settles it**: the three tballison pull requests already pinned at `~/evaluation/pull-requests/tika`. PR 3154's messages say inference engines and bindings; its written signals lead with `component`, `load`, `config`. The measure must separate that pair from a pull request whose message matches its diff, and the three divergences are published as readings of the pinned heads. **Abandon if** the safeguard cannot be demonstrated — a reading of the pull request's code with and without its prose supplied must be identical — or if the divergence on the three does not track the gap a person sees.

**Landed 2026-09-12, at reading schema 30.0.** `fetch-pull-requests.sh` writes `pr-<n>-statement.md` — title, description and commit messages verbatim, as the API states them at retrieval — and `pr-<n>-template.md`, the repository's own pull request template at the head commit, beside each directory and never inside it. The reading subtracts every statement line the template states verbatim (`AuthoredLines`: the untouched template is the host's prose, and the subtraction is cited to the repository's own published file), blanks HTML comments as markdown grammar (`MarkdownSource`, because no renderer shows them), reads what remains through the documentation pipeline (`ProseReading`), and publishes the Jensen–Shannon divergence against the changed files' reading in `pullRequests[].statement`, beside the bar `StatementNull` draws: 999 chance statements of the same sentence shape, filled from the tree's own written words at the reading's seed, the bar at the chance-expected furthest of the statements judged together. The safeguard is held by `ExportedPullRequestsTest`: the block with the statement and without it is identical outside `statement`, and a stated word never returns as a signal.

The three readings of the pinned heads, committed in `output/tika/json/reading.json`:

| Pull request | Sentences | Words | Divergence | Its bar | Chance rate |
|---|---|---|---|---|---|
| 3153 | 4 | 33 | 0.382 bits | 0.581 | 0.962 |
| 3154 | 2 | 13 | 0.460 bits | 0.712 | 0.989 |
| 3156 | 3 | 23 | 0.635 bits | 0.649 | 0.300 |

No statement diverges past its bar. The finding is the other tail: 3153 and 3154 sit closer to their changed files than 96 and 99 of 100 chance statements — each states the code it ships with — and 3156, whose authored prose is one line about a rename plus a merge commit's message, fits worst. This section's expectation that 3154 would separate as a gap conflated two instruments: its *signals* lead with `component`, `load`, `config` against English and the corpus, but in topic space "engines config section" and engine-configuration code agree. The subtraction demonstrated the hazard it exists for: before it, the shared template held every statement at ~250 words and the three divergences barely separated.

**Open here**: a statement below its bar publishes no per-topic decomposition, so the agreement the chance rate states is not yet named in topics — what a reviewer's sentence should say about agreement is section 4's question, and the change-process line in 3156's statement (`Merge branch …`) is section 6's.

## 2. The commit history as its own scope

The whole history's messages, read as one prose scope of the repository: `git log --format=%B` at the pinned HEAD, written to a file by a fetch step, handed to the reading by path.

The known obstacle is the vocabulary: the commonest commit words are `fix`, `add`, `test`, `bug`, `patch` — change-process words, not domain words — a finding as old as the [topic-model studies of commit logs](https://www.researchgate.net/publication/221554692_Mining_software_repositories_using_topic_models). The doctrine's answer is not a stop list; it is the machinery the signals already run: a **reference corpus of commit messages**, drawn from the ten reference repositories, so `fix` and `bump` are priced by what every repository's history writes and only the departure survives. The stream and its reference arrive together or not at all — a token cut from one side alone is promoted, not removed.

**The fetch step landed 2026-09-13.** `fetch-commits.sh` writes one repository's messages from the clone — `git log --format=%B` with a full stop between commits, which is what a prose reader takes as the end of a document — filtered to an author where one is named, and pins the commit the clone stands at in a `commits.tsv` beside them. A shallow clone holds one commit and says so rather than reporting an empty history, which is what every evaluation member is: reading one needs `git fetch --unshallow` first. Nothing reads the files yet; the reference corpus of commit messages this section turns on is the unbuilt half.

**What settles it**: the eleven members read with the commit-message scope and without it, and whether any member's placement moves toward the domain its manifest states. One member is a designed test case: `handcoded/fpml-toolkit-java` reads empty from its tree — 195 Java files no scope reaches — so its commit history is the first prose that could give it a non-empty reading at all. **Abandon if** commit prose places no member better than its README does; a README costs no fetch step.

## 3. Recency

The ask is that recent statements count for more. The precedents split: [windowed developer topic analysis](https://softwareprocess.es/x/x/lda-paper.20090409.214206.Apr.09.2009.pdf) reads topics per time window with no decay parameter; the fault-prediction literature uses weighted time decay. The doctrine decides between them: **a half-life is a chosen bound, and a bound must be derived, never chosen.** A window the repository itself states — a release tag, a dated era its history records — is citable; a decay constant is not.

So recency, if it earns its place, is per-window readings reported side by side, never a decayed pool. Two facts gate it behind the halves above: there is nothing to window until the commit scope exists, and a weighting change's blast radius must be predicted before it is built — a uniform per-word weight normalises out of the topic shares entirely and moves nothing, which has been measured here once already.

## 4. Constructing the sentence a reviewer reads

The pull request comment — use 4 of [what consumes the export](CONSUMING_THE_EXPORT.md) — has to render measured figures as English, and the sentence varies grammatically with the figures: one signal or nine, agreement or divergence, a vocabulary named or none. The candidate library is [SimpleNLG](https://github.com/simplenlg/simplenlg), the standard Java surface realiser — a *surface realiser* takes a subject, a verb and their attachments and produces the inflected, ordered sentence — at [V4.5.0](https://github.com/simplenlg/simplenlg/releases) under MPL 2.0, whose optional wide-coverage lexicon is the NIH SPECIALIST Lexicon, a published resource in the sense this library already cites. The alternative is what the pages do today: templates, with the [house prose rules](../../.claude/skills/written-english/SKILL.md) binding either way.

**What settles it**: whether the comment's sentences genuinely vary in structure. A realiser earns its dependency where templates would multiply — number agreement, aggregation of signal lists, tense — and is weight in the artefact where three templates cover the cases. Write the three tika comments both ways and count the template variants the plain path needs. A new dependency also passes the licence gate in `NOTICE.md`, and Maven Central is unreachable from the sandbox, so the artefact is seeded into `~/.m2` by hand.

## 5. Human-readable summaries of semantic content and of diffs

The research runs in three eras. Templates over static analysis: Sridhara's method summaries, ChangeScribe's commit summaries, Buse and Weimer's DeltaDoc, ARENA's release notes. Neural generation: from the first translation-style models to today's benchmarks — [CommitBench](https://arxiv.org/pdf/2403.05188) and [CommitSuite](https://arxiv.org/html/2605.02256) are the current references, and a [2025 survey](https://doi.org/10.3390/computers14100427) covers the prompt-only, fine-tuned and retrieval-augmented families. Evaluation of the summaries themselves: the BLEU-family metrics correlate poorly with human judgment, and [LLM-judged evaluation](https://arxiv.org/html/2507.10906v1) now outperforms them — which is a warning as much as a result, since a judged score is an assertion with no citation behind it.

**The doctrine's position writes itself**: a generated summary is an assertion, and an assertion is not evidence. What this library can publish as a summary is the sentence that *states its measurements* — the signals, the shares, the divergence, each with the workings behind it in the export — rendered by section 4's machinery. A neural summariser is admissible the way an embedding is: as a candidate generator whose claims the measured reading confirms, never as the finding itself.

## 6. Reading the diff itself: libraries, and the standards that name a change

The pull request path reads changed files whole, at the head commit. An AST diff reads the *change*: which declarations a commit adds, removes and moves. That is the parse of a change — grammar, in this library's sense, like the parse it already runs — and three tools carry the field: [GumTree](https://arxiv.org/pdf/2011.10268) (the influential general AST differ, two-phase matching, move operations), ChangeDistiller (the foundational tool, and the source of Fluri and Gall's published taxonomy of fine-grained change types), and [RefactoringMiner](https://dl.acm.org/doi/10.1145/3696002), whose threshold-free, refactoring-aware matching now measures more accurate than GumTree and detects the refactoring catalogue's types directly from history. The measurable refinement they offer here: a pull request's reading weighted to the declarations it *adds*, rather than every file it touches — settled, as ever, by whether the refined reading separates the tika three better than the whole-file reading does.

**The standards are the doctrinal prize.** A curated statement of a published standard is citable, and the change-description field has real ones: [Conventional Commits v1.0.0](https://www.conventionalcommits.org/en/v1.0.0-beta.2/) — `type(scope): description`, the `feat`/`fix`/`docs`/`refactor`/`perf`/`test` types, `BREAKING CHANGE`, each correlated with semantic versioning — plus Keep a Changelog's category set, Fluri and Gall's change-type taxonomy, the refactoring catalogue, and Swanson's corrective/adaptive/perfective triad from 1976. A `fix:` prefix parsed under Conventional Commits is **the specification's word, not the author's** — exactly the distinction that lets the reading set aside `final` and `return` without a stop list. So the change-process vocabulary of a commit history can be cited away by a bundled, provenance-headed statement of these standards, with the reference corpus of section 2 pricing whatever prose remains. That is a tiny vocabulary by this library's standards, and it goes through [the taxonomy-adding steps](../../.claude/skills/adding-a-taxonomy/SKILL.md) like any other: pinned source, licence read at the revision, header stating the publisher.

**The stated half landed 2026-09-13, at reading schema 31.0.** The specification is bundled through the taxonomy steps: `conventional-commit-types.tsv` carries eleven tokens — `feat`, `fix` and the `BREAKING CHANGE` footer with the v1.0.0 specification's own sentences at a pinned revision, and the eight types it names as recommended with the Angular convention's definitions at the revision the specification's own link pins; `chore` is named there and defined by neither source, so its definition is empty. `ConventionalCommitLine` is the grammar — a lowercase type, an optional scope, an optional `!`, the colon and space — and `StatedWork` keeps a parsed type only where the bundled standard states it, so `pullRequests[].work.stated` publishes `linesRead`, `linesParsed` and one row per stated class. **The first measurement came out as this section predicted**: the three pinned tika pull requests title by Jira key, so on all three `linesParsed` is 0 and `classes` is empty — abstention stated, never a guess — while every figure outside `work` is unchanged from the 30.0 reading. **The tracker's statement joined the stated side the same day.** A Jira key names an issue, never a kind of work, so the key is not mapped to a class: `fetch-pull-requests.sh` reads the tracker the repository's own pom names in `<issueManagement>` — a self-hosted server with a context path and a cloud site both resolve, the site root read off the stated `/browse/<KEY>` or `/projects/<KEY>` URL — finds that project's keys in the statement, and pins each referenced issue's own type and summary to `pr-<n>-issues.tsv`. `pullRequests[].work.issues` republishes the key, the tracker's type verbatim and the issue's page, never mapped onto Conventional Commits' vocabulary. Measured on the tika three: all reference TIKA-4889, and where the grammar abstains the tracker answers — Task, "Simplify inference configuration" — so each of the three carries a stated class from the tracker's side. The written classifier is what would answer from the diff itself, and it is the next half: the fetch step pins `base-sha` but writes no base files, so it grows a `pr-<n>-base/` directory, and the declaration diff reads against Fluri and Gall's change types and the refactoring catalogue — RefactoringMiner's statement of the catalogue is MIT and can bundle; ChangeDistiller's licence is unverified; Swanson's 1976 triad is ACM-paywalled and expected to stay out at the licence gate, as the ACM CCS did.

**The written half landed 2026-09-13, at reading schema 32.0.** `fetch-pull-requests.sh` writes `pr-<n>-base/` beside each pull request's directory: the paths already written at the head, each taken at the base commit from the clone the fetch already has, so a directory the script keeps costs no further call to the host and a file the pull request adds is written at the base not at all. `DeclaredMembers` is a parse of its own — the types, methods and fields of each tree's Java files, under the scopes the reading honours — and `DeclarationDiff` differences the two as a multiset keyed on the file, the enclosing declarations, the kind and the name. `pullRequests[].work.written` publishes what the head adds, what it removes, how many declarations stood at both, how many files the reading reaches, how many of those are new, and every type added and removed by name and path.

**Nothing is matched across a rename**, so a renamed method reads as one removed and one added; the alternative is a similarity heuristic asserting an intention the text does not state. The identity is coarse on purpose: PR 3156 changes `ContentEnricher` from `public interface ContentEnricher` to `public interface ContentEnricher extends Engine`, and the diff counts no type added and none removed, because the file, the enclosing declarations, the kind and the name all stand. Two overloads of one name are two declarations, and a third added is one added.

**No change class is named from the diff.** Two things are missing and both are open. A bundled standard that states one: Fluri and Gall's change types and the refactoring catalogue have not gone through [the taxonomy-adding steps](../../.claude/skills/adding-a-taxonomy/SKILL.md). And visibility in the parse: `NameForm` states what a name is and who chose it, never whether the published surface carries it, so the reading cannot yet say that a removed declaration is the incompatible API change [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html) defines — the one route by which the written side and the stated side would meet on a scale both standards state, since Conventional Commits states its own correlation of `feat` to MINOR, `fix` to PATCH and `BREAKING CHANGE` to MAJOR.

The three readings of the pinned heads, committed in `output/tika/json/reading.json`:

| Pull request | Files read | New files | Declarations added | Declarations removed | Standing at both |
|---|---|---|---|---|---|
| 3153 | 34 | 23 | 31 types, 145 methods, 75 fields | none | 312 |
| 3154 | 10 | 8 | 8 types, 39 methods, 18 fields | none | 75 |

That separates them from each other in a way the statement divergence does not — 3153 and 3154 introduce a subsystem, 3156 changes one that stands. The safeguard is the same with-and-without comparison the statement half holds, and `ExportedPullRequestsTest` pins it: the block with the base tree and the block without it are identical outside `work`.

**The measurements the diff carries, at reading schema 33.0.** Each pull request's `work.written` publishes, beside the declaration counts: which kind each read file is, decided by where the build looks for it — `production` for a source set the build publishes, `tests` and `fixtures` for the source sets that check it, `documentation` and `build` for the rest (`SourceKind`); the lines at each end, split into what the authors wrote as prose and everything else; the size and complexity of what each end declares, the complexity being [McCabe's](https://doi.org/10.1109/TSE.1976.233837) (`DeclarationMetrics`, `TreeMetrics`); and the types added to what the build publishes with no test of their own, where a test is a class whose name [Maven Surefire's default includes](https://maven.apache.org/surefire/maven-surefire-plugin/test-mojo.html#includes) would run (`SurefireTestNames`). That last figure says no test arrived with the type and never that nothing covers it — the reading runs nothing. **Each such type is named beside the test it arrives without**, at `pull-requests.json` schema 3.0: the name comes from the first of the same four patterns, `Test*`, and is read back through all four before it is published, so a subject those patterns cannot carry is named nothing rather than given a file name that build would not run. `AuthorUntestedTypes` draws the pair as a table, and `ReadingFolder.pullRequests()` declines a document published at another version, because a field added since parses as absent rather than as a failure.

**`testMethodsAdded` counts the tests that arrived**, at schema 4.0: how many of the methods a change adds carry the `Test` annotation, which is what [JUnit 4](https://junit.org/junit4/javadoc/latest/org/junit/Test.html), [JUnit Jupiter](https://docs.junit.org/current/api/org.junit.jupiter.api/org/junit/jupiter/api/Test.html) and [TestNG](https://testng.org/javadocs/org/testng/annotations/Test.html) each call it (`DeclaredTests`). A method Jupiter also runs under `ParameterizedTest`, `RepeatedTest`, `TestFactory` or `TestTemplate` is not counted: those carry Jupiter's own `Testable` annotation, and reading one annotation through another needs the classpath this parse does not have. A test method added to a class that already stood counts as readily as one arriving with its type, because the added declarations are the diff's and which of them a tree annotates is a second parse of the same files. The count says how many tests arrived and never what they exercise — no standard names a test method after its subject, and which methods a test runs would need the tests run, which this reading does not do.

**Duplication is measured as exact repeated method bodies, and on tika it is almost all accessors.** `RepeatedBodies` reads the changed files together, so a body copied between two of them is found as readily as one copied within a file. Two bodies are the same where the parse prints them alike, which makes layout no difference and admits nothing weaker than equality; a body carrying no statement is not counted however often it is written. **Two figures are published because one misleads**: the statements the repeating methods carry together, and the biggest repeated body. On the thirteen tika pull requests the totals rank 3160 worst at 45 statements — across 37 methods, whose biggest repeated body carries 3, which is `isEnabled`, `getText` and `getSupportedTypes` returning a field. The biggest-body figure ranks 3161 first at 4, and finds 3156's `unwrap` copied from the loader into its own test. No threshold separates them and none is stated: the reader is given both.

**The mapping from a measured shape to the standard's word is a bundled resource.** `change-shape-types.tsv` states one row per shape the reading can measure — the token, the measurement as a clause completing *it …*, the Conventional Commits type, and that publisher's own definition quoted beside it, so the pairing can be read one against the other rather than taken on trust. The file's order is the rule order and the first shape a change has answers, so a change confined to the source sets that check the published ones is `test` even where it adds declarations. `InferredChangeKind` holds the measurements and nothing else, and refuses to start where the file states a shape it cannot measure; widening the mapping is a change to a resource, never to a predicate. Its `Kind:` is `mappings`, a sixth kind admitted to `VocabularyProvenanceTest` for exactly this: a file whose rows are not a publisher's own, which is why each quotes the definition beside the measurement.

**Three of its seven rows name nothing, and say why.** Removing declarations and adding none is the one Semantic Versioning would call an incompatible change, which the specification correlates with the `BREAKING CHANGE` footer — but `NameForm` states which declaration a name is and who chose it, never whether the published surface carries it, so the reading cannot tell a removal from the published API from a removal of something private. Adding and removing together is covered by more than one definition. Changing only method bodies is covered by both `fix` and `refactor`, whose definitions the Angular convention writes as each other's negation. Naming any of those would be a guess. A tracker type is not mapped at all: Jira states `Task` as work to be done and names no kind of change, where `Bug` and `New Feature` would coincide with `fix` and `feat` by both publishers' definitions. On the tika three, the shape answers `feat` for all three where their statements name nothing.

**The pull request analysis is its own published document, at `pull-requests.json` schema 1.0.** It answers a different question about a different corpus — the reading is of a working tree at one commit, this is of the changes proposed against it — so it is a file of its own, checked against `pull-requests.schema.json` before it is written, and `reading.json` carries no `pullRequests` block at all from schema 34.0. A consumer wanting one and not the other reads one file, and the repository's own figures cannot move when this shape does. `./gradlew pullRequests -Dcs.clone.dir=… -Dcs.pullrequests.dir=…` is the whole path in one command: the reading, the pull requests fetched beside it, and the pages drawn from both.

**Each pull request's words are matched against every bundled vocabulary.** `concepts` publishes what a publisher states for the terms the changed files write — on tika's 3153, OLiA's `document`, FpML's `mime type`, FIX's `text`. They are matches and not a placement: a repository is placed only where a vocabulary writes more of its phrases than a deal of that vocabulary's own words reaches, and that bar is drawn over a whole tree, so a few changed files are too small a field for it. No vocabulary is judged to have answered.

**The report is read without colour.** Each figure in the spread table carries a mark whose outline names its band — a tick at or below the repository's median, a dash up to its upper quartile, a cross above it (`MetricBand`) — so nothing there is carried by hue alone, and the legend names all three. The header answers the reviewer's first question directly: whether these pull requests' methods are more complex than the ones already there, both figures upper quartiles. **Not medians** — tika's median complexity is 1 and so is nearly every pull request's, so a median reports the two equal whatever the change did; three quarters of the way up the methods is where the measure moves, and it is the bound the marks are drawn at. The pull requests' own figure is the middle one's, and a change declaring no method is read past rather than counted as nought: on tika the sentence separates timgrein and TianHengZhuang at 5 against tika's 2 from tballison and dschmidt at 2, and says of THausherr's pom-only changes that there is nothing to compare. A second sentence counts the changes whose *worst* method sits past that centile, which the comparison cannot say: dschmidt's methods are typical at the 75th centile and one change still carries a method past anything tika holds. Every subject a vocabulary states is written in italics, as the words beside it are.

**Each report opens with the whole of itself in seven lines.** `AuthorOverview` states one line per question the sections answer — how many, what they are about, what kind of change, what they change, what arrives tested, what the code looks like, how well the descriptions fit — each linked to the section carrying the figures behind it, and each figure a total of figures those sections state again in full (`AuthorTotals`). Every sentence agrees with the number of pull requests, so an author who opened one reads *This pull request adds* and *It declares no method*.

**The reports read the two halves together.** `./gradlew pages` writes one report per author per repository — `tballison.html` beside tika's own findings page. It once opened with three lines: how much the author's pull requests change, what kind of change they are, and what their code is about. Four tables follow, a row per pull request: what each of the three sources calls the change and the shape the third rests on; how many files of each kind it touches and what it declares in them; the lines it adds, the types it adds no test for and the four complexity figures; and the words its changed files write above both references, how many of those the repository's own reading does not carry, and how well its description fits its code. Words a dictionary calls one word are merged, each pull request's words are drawn as a cloud, and the counts link to the lists behind them. The repository's findings page names each author and links to their report.

## Order

**Reordered 2026-09-13, on Pippa's direction**: the pull request summary must *classify the work done* against the published standards, not only state its subject matter. So section 6's standards bundle and diff reading come next, with section 4 rendering the classification, and section 2 follows them. **Both halves of the classification now stand**: the statement parsed under Conventional Commits with the tracker beside it, and the declaration diff. What remains of section 6 is the naming — a bundled change-type taxonomy, and the visibility the parse does not carry. The classification is two independent readings, one per side section 1 already keeps apart: what the pull request *says* it is — its title and commit messages parsed under [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0-beta.2/) (`feat`/`fix`/`refactor`/`perf`/`docs`/`test`), with [Swanson's corrective/adaptive/perfective triad](https://dl.acm.org/doi/10.1145/800253.807723) and Keep a Changelog's categories as the coarser statements — and what it *writes*, the diff's added, removed and moved declarations read against Fluri and Gall's change-type taxonomy and the refactoring catalogue. Each standard bundles through [the taxonomy-adding steps](../../.claude/skills/adding-a-taxonomy/SKILL.md); a statement no standard's grammar parses yields **no stated class rather than a guess** — the three pinned tika pull requests title in Jira style, so the stated classifier abstains on them and the written classifier still answers, which is the first thing to measure. Agreement between the stated class and the written class is the finding, exactly as section 1's divergence is, and neither side answers for the other.

1 before 2, because 1's data is fetched and pinned, its machinery landed at schema 28.0, and its safeguard test is the same with-and-without comparison already demonstrated on tika. 2 next, with its reference corpus arriving in the same change — and the Conventional Commits statement of section 6 beside it, because citing the change-process words and pricing the remainder are two halves of one reading. 3 only after 2, and only by windows the repository states. Sections 4 and 5 are consumers: they render what 1 and 2 measure, and the sentence-construction decision waits until there are three real comments to write. The AST-diff refinement of section 6 is last; it sharpens a reading that has to exist first.
